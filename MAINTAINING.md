# Сопровождение share-ui из consumer-проектов

Этот runbook описывает рабочий процесс для изменений общей библиотеки, которые
обнаруживаются во время задач в DnDShare, HavenShare или TrenchShare. Архитектура
пакета остаётся в [`docs/architecture.md`](./docs/architecture.md), публичный API —
в [`docs/components.md`](./docs/components.md), а детали выпуска — в
[`docs/development.md`](./docs/development.md).

## Разрешение на cross-repository работу

Задача в consumer-проекте даёт разработчику или автоматизированному агенту
разрешение без отдельного согласования изменить соседний репозиторий `share-ui`,
если общий компонент, токен или interaction-механика действительно нужны для
завершения этой задачи.

В рамках такого разрешения можно:

- исследовать и редактировать `share-ui`;
- добавить или изменить тесты, галерею и документацию;
- собрать `dist/`, создать commit, выпустить неизменяемый Git tag и отправить
  branch/tag в `SylvieShare/share-ui`;
- обновить точный tag и lock-файл в инициировавшем consumer;
- обновить другие consumers, если это необходимо для совместимости изменения.

Разрешение не распространяется на несвязанные рефакторинги, удаление чужих
изменений, секреты и разрушительные Git-операции. Перед правкой нужно проверить
`git status` всех затрагиваемых Git-репозиториев и сохранить посторонние изменения.
Если безопасный выпуск требует существенно большего продукта или breaking-
миграции, которую нельзя завершить в текущей задаче, работа останавливается до
решения пользователя.

## Где должен жить код

Код относится к `share-ui`, когда он:

- выражается через props, emits, slots или нейтральный composable;
- использует публичные semantic tokens;
- не знает про router, Pinia, HTTP API, авторизацию, i18n и доменные сущности;
- имеет минимум два реальных или обоснованно запланированных consumer-сценария
  либо исправляет уже существующий общий контракт.

Код остаётся в consumer, если он знает о маршруте, store, запросах, правах,
локализованных продуктовых текстах или предметной модели. В таком случае
consumer создаёт тонкий adapter/controller поверх примитива библиотеки.

```text
share-ui: presentation + transient UI state + browser interaction
consumer: router + stores + API + permissions + domain data + persistence
```

Нехватку API общего компонента не обходят копированием реализации, deep import,
правкой `node_modules` или постоянным CSS-переопределением его базовой геометрии.
Сначала расширяется нейтральный публичный контракт. Локальный аналог допустим
только для отдельного UX, который нельзя выразить общим API; причина фиксируется
в wiki consumer-проекта.

## Рабочий процесс

1. Прочитать инструкции инициировавшего consumer и `share-ui`, затем проверить
   рабочие деревья.
2. Сверить задачу с публичным API, `ComponentGallery` и критериями включения.
3. Сформулировать нейтральный контракт без импортов и терминов consumer-проекта.
4. Реализовать изменение в исходниках `share-ui`.
5. Одновременно обновить типы, public exports и `docs/components.md`, если
   меняется публичный API.
6. Добавить или обновить unit/component tests. Каждый публичный визуальный
   компонент и его основные состояния добавить в `ComponentGallery`.
7. Обновить архитектурную, theming- или migration-документацию, если контракт
   или правило изменились.
8. Выполнить проверки библиотеки и временную интеграцию с consumer.
9. Если изменились устанавливаемые файлы, выпустить новую версию и tag.
10. Вернуть consumer на точный HTTPS URL tag, обновить lock-файл, выполнить его
    проверки и закончить исходную задачу.
11. При изменении общего default или критичной механики проверить остальные
    затронутые consumers до выпуска либо в том же coordinated change.

## Локальная интеграция

Для проверки незарелизованной версии разрешена временная установка соседней
папки:

```bash
cd /Users/wrz2/MyProjects/<consumer>/frontend
npm install /Users/wrz2/MyProjects/share-ui
```

Абсолютный путь и `file:` dependency не коммитятся. Перед завершением consumer
обязан использовать точный HTTPS-архив неизменяемого tag:

```bash
npm install --save-exact \
  "https://github.com/SylvieShare/share-ui/archive/refs/tags/vX.Y.Z.tar.gz"
```

Нельзя проверять только содержимое уже существующего `node_modules`: итоговая
сборка должна пройти после установки release tag, который будет использовать CI
и production.

## Версии и выпуск

- Patch (`0.x.Z`) — обратно совместимый bugfix, внутреннее улучшение или
  корректировка визуального поведения в рамках существующего контракта.
- Minor (`0.X.0`) — новый публичный компонент/API. До `1.0.0` сюда же относится
  breaking change, который должен быть явно отмечен и сопровождаться миграцией
  всех затронутых consumers.
- После `1.0.0` breaking change увеличивает major.
- Изменение токенов, базовых размеров или visual defaults считается
  compatibility-sensitive даже без изменения JavaScript API.
- Документация, не меняющая устанавливаемый пакет, не требует новой версии/tag.
- Опубликованный tag не передвигается; исправление выпускается новой версией.

Перед tag нужно изменить `package.json`, выполнить `npm run check`, проверить
документацию и собранный `dist/`, создать release commit и аннотированный tag,
затем отправить branch и tag. Полные команды находятся в
[`docs/development.md`](./docs/development.md).

## Матрица проверок

| Изменение | Обязательная проверка |
|---|---|
| Документация без изменения пакета | Ссылки, согласованность README/docs, чистый diff |
| Внутренний refactor или bugfix | `npm test`, `npm run build`, `npm run check` |
| Новый публичный API/компонент | Проверки библиотеки, типы/exports/docs, gallery coverage, build/tests инициировавшего consumer |
| Tokens, `BaseTile`, forms, overlays, sidebar, canvas или DnD | Проверки библиотеки и build затронутых DnDShare, HavenShare и TrenchShare; релевантные тесты consumers |
| Breaking change | Одновременная миграция всех затронутых consumers и проверка release tag в каждом |

Для любого устанавливаемого релиза дополнительно выполняется `npm pack --dry-run`.
Warnings не скрываются: известные предупреждения отмечаются в handoff, новые
ошибки исправляются до выпуска.

## Definition of Done

Изменение общей библиотеки завершено, когда:

- код находится на правильной стороне границы library/consumer;
- public API доступен только через `@sylvieshare/share-ui` без deep imports;
- типы, тесты, документация и `dist/` соответствуют исходникам;
- публичный визуальный компонент представлен в `ComponentGallery`, coverage
  проходит;
- выпущен новый неизменяемый tag, если пакет изменился;
- consumer установлен с этого tag, его lock-файл, тесты и production build
  обновлены;
- другие consumers не сломаны либо мигрированы в том же изменении;
- wiki каждого изменённого consumer описывает актуальное состояние.

Исходная consumer-задача не считается завершённой на временной `file:`
dependency или на незапушенном изменении `share-ui`.
